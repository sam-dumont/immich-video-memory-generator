# Trip Memories

Nothing declares a trip. The GPS on your own pictures decides where one starts and where it ends, and each trip gets its own video, opening on a satellite map of the route.

only the title on a flat panel. `make demo-output-trip` cuts this clip again.

## How trip detection works

Three stages, no clustering:

1. **Keep what is away from home**: an asset survives if it has GPS coordinates *and* they are at
   least `min_distance_km` from your home (default: 50 km). Assets with no GPS are dropped here.
2. **Split on gaps**: the survivors are sorted by capture time and a new trip starts wherever more
   than `max_gap_days` (default: 2) passes between one asset and the next. The gap is measured
   asset to asset in fractional days, not between calendar days, so a rest day does not split a
   trip.
3. **Discard the short ones**: a group survives if the number of *nights* it spans, the difference
   between its first and last calendar date, is at least `min_duration_days` (default: 2). At the
   default that means three calendar days. `1` catches a weekend away, and it is the floor: the
   field is `ge=1`, so `0` fails validation.

The trip's name comes from reverse geocoding the centroid of all GPS coordinates in the cluster (via Nominatim/OpenStreetMap), and that name is what the title screen shows.

## CLI

Detect and list all trips for a year:

```bash
immich-memories generate --memory-type trip --year 2025
```

This shows a table of detected trips with dates, location, and asset count. You then select which trip to generate:

```bash
# Generate a specific trip by index
immich-memories generate --memory-type trip --year 2025 --trip-index 2

# Generate all trips
immich-memories generate --memory-type trip --year 2025 --all-trips

# Closest trip to a month
immich-memories generate --memory-type trip --year 2025 --month 7

# Closest trip to a specific date
immich-memories generate --memory-type trip --year 2025 --near-date 2025-07-15
```

`--person` narrows trip **detection**, not the finished video. `--person "Their Name"` looks for trips among the assets that person appears in, which helps when one person's phone is the one carrying GPS. Each video is then built from everything shot in that window, so the rest of the group is still in it.

## Web UI

Pick **Trip** on the [Memory page](../web-ui/memory.mdx) and a year; the page runs trip detection
and lists the trips it found. Select one and press **Cut**.

One difference from the CLI worth knowing: the page detects trips from **videos only**, while the
CLI reads every asset type. A trip you only photographed will not appear here. Use the CLI for
those.

## Duration

Auto starts at 30 seconds plus 10 seconds per active day, bounded to 60-300 seconds when there is enough material. Seven dense days produce about 1:40; 12 dense days produce 2:30. It then checks the selected media's usable excerpts and shortens sparse trips instead of promising time it cannot fill. Turn off the **Auto duration** switch on the Memory page, or pass `--duration`, when you want an exact runtime.

## Configuration

```yaml
trips:
  homebase_latitude: 48.8566    # Your home latitude (required)
  homebase_longitude: 2.3522    # Your home longitude (required)
  min_distance_km: 50           # Minimum km from home to count
  min_duration_days: 2          # Minimum days to qualify as a trip
  max_gap_days: 2               # Max gap before splitting trips
```

The homebase coordinates are required: without them nothing counts as away. Get them wrong and you either collect your own neighbourhood or lose real trips. Lower `min_distance_km` to about 20 km if you want weekend drives to the next city to register.

## When it finds nothing

GPS is the whole input. Some cameras strip it and screen recordings never had it, so a library shot on a camera rather than a phone can come back with nothing while looking full of holidays. Phones embed GPS by default.
