# The UX audit of `release/story-first`

2026-09-12. An audit of the release branch from a user's seat, and the plan that
follows from it. Nothing here is implemented; the process comes first and the UI
is repaired after it. This document is the record so the work does not have to be
re-derived.

Read at `release/story-first` (`42f0ce9d`). Every path is repo-relative.

## What prompted it

Running the branch end to end, as a person rather than as a test:

- A cut runs for minutes and says almost nothing about where it is. No estimate,
  no counts for the long phase, no sense that anything is happening.
- The CLI and the web UI report the same run through entirely separate plumbing,
  so neither can be the reference for the other.
- The result reads as a ranked list of stories, not as the video that was planned,
  and never shows every picture that was considered.
- Settings → People reloads the browser on every change.
- A Chrome tab grew during a cut until it blocked the machine.

The product has two audiences and serves neither cleanly. A scheduler runs many
memories unattended and has no face in the UI at all. A person building one
ad-hoc video gets a single Cut button with no way to see or change what the
editor decided.

## Decisions taken before this was written

| Question | Decision |
|---|---|
| Issue structure | One umbrella issue; #809 closes into it |
| Auto mode in the UI | A Suggestions page **and** a Runs page |
| Result view | Add a chronological storyboard, keep the ranked story |
| Release scope | All of it lands before the release |

# Part 1 — What is wrong

## 1. Two unrelated progress systems

|  | Editorial cut (the new flow) | Render / export (old step 4) |
|---|---|---|
| Contract | `Callable[[dict], None]`, declared inline twice, no alias — `analysis/smart_pipeline.py:79`, `:88` | `Callable[[str, float, str], None]` plus `PhaseEvent` — `generate.py:174`, `operations/phases.py:33` |
| Carries | `phase_label`, `status`, `started_at`, `elapsed`. `indeterminate` is hard-coded `True` — `analysis/editorial_projection.py:48` | phase name, a real fraction, a message |
| Reaches the UI | **not through the callback** — the page polls two JSON files on disk each second | directly, by callback |

`operations/phases.py:10` holds the one canonical enumeration, `OperationalPhase`,
eight values with a stable `.order`. Three other vocabularies compete with it: the
UI's five-value `CUT_PHASES` with its own titles (`ui/pages/memory_run.py:52`), the
weight keys in `generate_progress.py:123`, and eleven free-text stage strings
scattered across the editorial modules.

Of the fifteen keys in `ui/pages/clip_pipeline.py:82`, thirteen are never written
by anything. The dict is never read for display either — `memory_run.py:324` reads
only `error`. In practice that callback is a cancellation probe.

## 2. The keystone: one line drops the numbers

`analysis/editorial_runtime.py:485` computes real counts and hands them to a
writer that returns them, then throws them away:

```python
def progress(stage: str, done: int, total: int) -> None:
    if done not in {0, total} and done % batch_size:
        return
    if on_stage is not None:
        on_stage(live.publish(stage, done, total).stage_label)   # a string
```

`on_stage` is `Callable[[str], None]`, so `done` and `total` die here.
`EditorialStageReporter.__call__` (`analysis/editorial_projection.py:44`) then
hard-codes `"indeterminate": True` into the dict the CLI reads.

Every symptom follows from that seam:

- **The UI bar only appears for five stages.** `StageBar` renders only when the
  attempt's stage string matches `f"Preparing {label}: {done}/{total}"` exactly
  (written at `operations/cut_progress.py:49`, compared at `memory_run.py:165`).
  Only the per-asset preparation passes produce it.
- **The CLI's estimator is switched off exactly when it is needed.**
  `cli/_live_display.py:333` appends `~N remaining` only when the active task has a
  total. `_SourceProgressReporter._unbounded_stage` (`cli/_pipeline_runner.py:249`)
  calls `progress.reset(task, total=None)` because the status says indeterminate.
  The one estimator the product owns is disabled for the longest phase.
- **The phase is guessed from a string prefix** (`ui/pages/memory_run.py:170`):
  `startswith("Preparing")` means ANALYSIS, anything else means SELECTION. Rename a
  label and the phase rows silently mis-classify.

## 3. The long phase says four things

The whole Editing stretch is four strings from `analysis/editorial_orchestration.py`
— `"Building editorial cards"` (`:166`), `"Editing the memory"` (`:177`),
`"Reading event evidence"` (`:188`), `"Reading the period account"` (`:204`).

`analysis/editorial_structure_planner.py:514` already maintains a `selection_stages`
dict with counts at `before_picture_review`, `after_shareability` and
`after_final_duplicate_review`, persists it, and nothing ever reads it.

A dead reading provider looks identical to a busy one: `analysis/llm_query.py`
retries three times with 2 s then 4 s of backoff before raising, saying nothing for
roughly six seconds. The retry is correct and must stay — a dropped connection once
killed a 26-minute run, and the ruling is that it is never fatal. What is missing is
that nobody is told.

## 4. A real bar bug on export

`generate_progress.py:111` promises the bar "only moves forward, never jumps
backward". Nothing enforces it, and `report()` maps an unknown phase to the whole
range:

```python
start, end = self._ranges.get(phase, (0.0, 1.0))   # generate_progress.py:142
```

`_ranges` holds `download`, `assembly`, `music`. Live call sites emit `"extract"`
(`generate_clips.py:244`), `"upload"` (`generate_delivery.py:86`) and `"done"`
(`generate.py:736`). Clip extraction sweeps the bar to full, then it snaps back.

## 5. The browser memory bomb

Every image in the app is a base64 data URI of Immich's **preview**, not a
thumbnail. `get_thumbnail` returns `state.thumbnail_cache.get(asset_id, "preview")`
(`ui/pages/step2_helpers.py:23`), fetched as `size="preview"` at
`step2_loading.py:403` and `:447`. The codebase states the size itself:
`cache/thumbnail_cache.py:118` budgets "roughly 0.35 MB per candidate asset".

That JPEG becomes roughly half a megabyte of base64 in a DOM attribute plus about
six megabytes of decoded bitmap in the renderer, dropped into cells sized
`minmax(140px, 1fr)` (`clip_grid.py:352`). Two hundred cells is over a gigabyte.

Three multipliers on top:

- `ui/pages/clip_grid.py:409` `_render_paginated` **appends** each new page into the
  same container and never clears it.
- `ui/pages/clip_review.py:395` renders one `<video>` per selected clip with no
  pagination, and starts a preview loader for every row regardless of whether its
  expansion is open (`:283` controls only the fold). `ui.video(Path(...))` goes
  through `app.add_media_file`, which registers a route per file and never removes
  it. `tests/test_ui_media_routes.py` exists because this was already learned once.
- `ui/pages/step4_export.py:72` starts a five-second timer, never deactivates it,
  and its action is `ui.navigate.reload()`.

The live progress strip is the one place that got this right: it re-encodes to 96 px
at quality 70 before sending (`ui/pages/cut_progress_view.py:67`). The cut-progress
view is **not** the leak. It is bounded by construction — a fixed picture ring, a log
that deletes its own overflow labels, four arrivals per tick.

## 6. Clicking a thumbnail reloads the page

The compact grid's toggles end with `ui.navigate.to("/step2")` — `clip_grid.py:247`
for photos, `:310` for clips. That is a real browser navigation: it re-runs the page
builder, re-encodes every base64 thumbnail and collapses pagination back to the
first twenty. The card-view checkboxes (`clip_grid.py:171`, `:215`) perform the same
mutation for free.

The wizard's person picker does **not** reload; it writes to
`state.memory_preset_params` and calls `apply` (`step1_people.py:126`, `:211`,
`:269`). The reloads are on **Settings → People**: `ui/pages/settings_people.py:357`,
`:410`, `:446`, each re-fetching every face crop. That page also writes the whole
people YAML on every role change and every debounced keystroke (`:292`, `:307` →
`people/companion.py:112`, whose own docstring says it rewrites the entire
document), renders an unbounded roster (`:209`), and fetches thumbnails one request
per person (`:149`, docstring: "a household of seventy is seventy round trips").

## 7. The result is ranked, not the video

```python
# ui/pages/memory_story_data.py:168
entries.sort(key=lambda entry: (_weight_rank(entry.weight), entry.day))
```

Stories come out ordered by editorial weight. The video is always chronological, so
the page never shows the cut in shot order. `state.timeline_plan` exists but is only
ever passed to the generator (`_step4_generate.py:248`, `:288`); nothing renders it.

Only granted carriers appear. `/step2` shows the full pool but hides itself the
moment a cut exists (`step2_review.py:107` returns early), so after a cut the grid is
unreachable until "Start Over".

This is also why a loose grouping reads as random: every carrier a story was granted
appears under one title, with nothing showing the days it actually spans.

## 8. A tick does not survive the cut

`clip_pipeline.py:363` passes unticked media to the editor as
`owner_excluded_asset_ids`, so the negative works. There is no positive. After the
run, `_adopt_result` overwrites the user's choices:

```python
state.selected_clip_ids = {c.asset.id for c in result.selected_clips}  # clip_pipeline.py:424
```

"Add a picture the pipeline rejected" therefore means keep it ticked, press Cut and
hope. This is the same defect users reported as #778.

**Bug found while reading.** `_recut` (`ui/pages/memory.py:57`) reuses
`_start_over_selection` (`step2_review.py:42`), which empties `selected_clip_ids` but
leaves `state.clips` populated. `memory_run.py:388` then sees `pool_loaded` true,
skips the reload, and `_set_initial_selection` never re-runs — so "Cut again" runs
with zero eligible videos and whatever photos the previous cut left behind.

## 9. The decision log exists, is complete, and nothing renders it

`analysis/selection_trace.py` was written for exactly this question. It carries
`ClipStory` with `dropped_at` and `reason` (`:44`), `Stage.notes` mapping asset id to
reason (`:59`), `TraceDecision` (`analysis/editorial_contracts.py:236`),
`PassTrace.rejected` and `.unresolved` (`:254`), and a `ConservationCheck` proving
every input got exactly one fate. `Trace.report()` renders "why each clip is in the
cut" and "and why the rest are not". `Trace.story_of(asset_id)` answers the
single-picture question directly.

It is armed only by `generate --trace-selection <path>`
(`cli/generate_options.py:222`), writes two files nothing reads back, and when it is
off the reasons are never built (`:515`). No UI code mentions it.

`plan.private.json` is written by **every** run, carries a per-carrier `why` and the
moment grouping, and is read by exactly one module — the web UI's
`ui/pages/memory_story_data.py`. The CLI writes it on every run and cannot print it.

## 10. The scheduler has no face

`ui/app.py:589` starts `automation_scheduler.run_forever()` inside the web process.
`ui/trigger_api.py` exposes a parameterless `POST /api/trigger` that runs exactly the
decision `auto run` would make. `tracking/` keeps a `pipeline_runs` table with
status, `last_phase`, timestamps, delivery status and the Immich asset id.
`automation/status.py` has a read-only status contract; `automation/notifications.py`
sends completion notices.

None of it is rendered. No automation page, no run history, no button for the
trigger. The sidebar still shows a four-step wizard whose step-2 checkmark is
`len(state.selected_clip_ids) > 0` (`ui/app.py:131`), a rule from the old flow.

Auto mode decides seven things (`automation/generation_request.py:108`: memory type,
scope, people, upload, album, plus identity flags) and carries **no** duration,
music, orientation, resolution, transition or title — those fall out of defaults, and
`AutomationConfig` (`config_models_automation.py:35`) has no key for any of them.
`auto run` accepts only `--dry-run/--force/--cooldown/--upload/--quiet`; there is no
way to pin a candidate or run the second suggestion. The scheduled child runs as a
subprocess on a pipe, so it takes the `QuietDisplay` path, and on success its entire
output is discarded (`automation/runner.py:271` keeps tails only on failure).

## 11. Two smaller things

- **No verbosity control.** `configure_logging()` is called with no arguments from
  both `cli/__init__.py:67` and `ui/app.py:623`. The level is `INFO`, always.
- **Per-phase elapsed is computed and dropped.** `PhaseEvent.elapsed_seconds`
  (`operations/phases.py:41`) is set on every transition and stored nowhere, so
  `runs show` can print only the three phases the run tracker records — its own
  docstring admits analysis and selection are missing.

# Part 2 — The plan

Eight streams, ordered so each unblocks the next. One PR per stream, split further
where a stream exceeds roughly 300 lines.

## W1 — One progress record, rendered by both surfaces

The keystone. Everything about progress follows from widening one seam.

- `operations/cut_progress.py` gains a `StageUpdate` carrying phase, label, `done`,
  `total` and recent asset ids. `StageProgress` folds into it.
- `operations/editorial_attempt.py` stores the whole record rather than a sentence,
  which removes the string-equality coupling at `memory_run.py:165` and the
  `stage_label` formatter at `cut_progress.py:49`.
- `analysis/editorial_runtime.py:485` passes the record through instead of
  `.stage_label`. `on_stage` becomes `Callable[[StageUpdate], None]`.
- `analysis/editorial_projection.py:44` forwards `done`/`total` and drops the
  hard-coded `indeterminate`.
- `ui/pages/memory_run.py`: `phase_of` reads the phase off the record. Delete the
  `startswith("Preparing")` guess and the label equality check. `StageBar` renders
  for any counted stage.
- `cli/_pipeline_runner.py`: `_SourceProgressReporter` sets a real total when the
  update carries one, which re-enables `_build_time_line`'s estimate for free.
- Delete the thirteen dead keys in `clip_pipeline.py:82` once nothing reads them.

Parity then becomes structural rather than a convention. Extend
`tests/test_surface_parity.py` with a progress case: one fake run, both reporters,
the same stage sequence and the same counts.

## W2 — The long phase reports

- Emit counted updates from the four silent stretches in
  `analysis/editorial_orchestration.py` (`:166`, `:177`, `:188`, `:204`), counting
  the episodes they already iterate.
- Surface the `selection_stages` counts already kept at
  `editorial_structure_planner.py:514` instead of writing a record nobody reads.
- Name an unreachable provider at once. `analysis/llm_query.py` announces the
  endpoint and what it is for on the first transport failure rather than after six
  silent seconds. The retry itself does not change.

**Hard constraint**: not one prompt byte, and nothing a digest is computed over. The
ten editorial routes must still replay byte-identical.

## W3 — Time remaining, honestly

- Within a counted stage: rate times remaining items.
- Across the cut: persist `PhaseEvent.elapsed_seconds`, computed and thrown away
  today, into the run database, and estimate from prior runs on the same library.
  Until there is history, say so rather than inventing a number.
- Where a stage genuinely has no unit, it says what it is doing. No fake percentage.
- Fix the export bar: clamp it monotonic, and map every phase name that is actually
  emitted (`extract`, `upload`, `done`) in `generate_progress.py:123`. Add a test
  that fails when a call site emits a name `_ranges` does not know.

## W4 — Stop the browser dying

- **One parameterised media route**, auth-gated, serving bytes from the session
  thumbnail cache with cache headers. Never `app.add_media_file` per asset — that is
  what `tests/test_ui_media_routes.py` guards. The route must honour demo and privacy
  blurring, which today happens at render time.
- Grids request and serve `size="thumbnail"`; `"preview"` stays only where a large
  image is genuinely shown. Where an intermediate size is needed, reuse the re-encode
  already written at `cut_progress_view.py:67`.
- `<img src="/media/…" loading="lazy">` instead of data URIs, so the browser caches,
  decodes lazily and evicts.
- `_render_paginated` (`clip_grid.py:409`) windows the DOM instead of appending
  forever.
- `clip_review._render_review_selected_clips` paginates, starts a preview only when
  its expansion opens (the pattern `_make_lazy_loader` already uses for month
  panels), and releases the video element on close.
- Drop `ui.navigate.to("/step2")` from `clip_grid.py:247` and `:310`.
- Deactivate the reload timer at `step4_export.py:72`.

## W5 — The result reads as the video

- **Storyboard tab, default.** Every carrier in capture order, since the cut is
  always chronological, with its duration, a running timecode, chapter dividers where
  the title planner puts them, and the story title as the chapter label. Sources
  already written per attempt: `plan.private.json` carriers and
  `render-projection.private.json` intervals.
- **Story tab** keeps today's weight-ranked thesis view unchanged.
- **The whole pool, with each asset's fate.** Turn `selection_trace` on for every run
  rather than only under `--trace-selection`, and render "in the cut" or "dropped at
  *stage* because *reason*" against every candidate. This is the single change that
  answers "why is that picture not in there".
- Give the CLI the same reading: `runs story <id>` prints the storyboard,
  `runs why <asset-id>` prints `Trace.story_of`. Both read records the CLI already
  writes.
- Reconcile the two cut keys so the UI can find a CLI run's attempt:
  `cli/_editorial_context.py:79` and `ui/pages/clip_pipeline.py:291` compute the
  directory name independently and differently today.

## W6 — Fine-tuning that sticks

- Fix `_recut`: re-run `_set_initial_selection` after the reset, or give it a reset
  that keeps the pool ticked (`ui/pages/memory.py:57`, `step2_review.py:42`).
- **A tick that survives the cut.** Add `owner_required_asset_ids` beside the
  existing `owner_excluded_asset_ids`, carried through `EditorialSelectionRequest`
  (`analysis/selection_source.py:124`) and honoured at carrier selection the way the
  `favourite` flag already is (`editorial_story_carriers.py:93`, `:362`). It is a
  post-read admission signal, so it changes no prompt. Closes #778.
- Settings → People: replace the three `ui.navigate.reload()` calls with a roster
  redraw reusing the `thumbnails` dict already in scope, paginate the roster, batch
  the thumbnail fetches through the W4 media route, and coalesce the YAML write
  instead of rewriting the document per keystroke.

## W7 — The scheduler gets a face

- **`/suggestions`** — what auto would pick right now: candidate, score, category,
  window and reason, plus the rejected candidates with the variety rule that rejected
  them (`automation/variety.py:56` already names all four). Each row offers "Cut this"
  and "Open in the brief" so a user can adjust before cutting. Reuse
  `AutoRunner.suggest`; it takes a library snapshot, so it needs a spinner and a
  cached result.
- **`/runs`** — the `pipeline_runs` table: phase, outcome, duration, delivery state
  and the Immich link. Reuse the shaping in `cli/runs.py:119`.
- Sidebar becomes Memory / Suggestions / Runs / Media pool / Settings. Delete
  `_is_step_complete`'s stale step-2 rule (`ui/app.py:126`).
- Give `auto run` a `--candidate`/`--memory-key` so the terminal can do what the page
  does, and keep the successful child's output instead of discarding it
  (`automation/runner.py:271`).

## W8 — Housekeeping the audit turned up

- A verbosity flag on both entry points; `configure_logging()` takes its level from
  nothing today.
- Finish the reader-word mapping started in `WEIGHT_LABELS`
  (`memory_story_data.py:27`), per launch-readiness item 4.18.
- The deprecated `scheduler` command group warns in prose only; either remove it or
  make it refuse.

# Constraints that bound every change

- **Byte-identical replay.** The ten editorial routes must still replay unchanged. No
  progress work may touch a prompt byte or a digest input. Guards:
  `tests/test_replay_editorial_routes.py`, `tests/test_matrix_routes.py`.
- **No per-asset media routes.** `tests/test_ui_media_routes.py` exists because
  `app.add_media_file` registers a route per call and never removes it.
- **Repo gates**: 800 lines per file, Xenon grade C, complexipy at most 15, roughly
  300 lines per PR, one concern per PR, a linked issue, conventional commits.
- Docs are owed for every user-facing change: `docs-site/docs/create/web-ui/`,
  `create/cli/`, `reference/`, and `sidebars.ts` for the two new pages.

# Verification

The harness already exists and is good.

| Check | Command | What it proves |
|---|---|---|
| Unit and gates | `make ci` | nothing regressed |
| Hermetic browser | `make e2e` | `tests/e2e/` has a fake Immich, fake library and fake editorial; `test_memory_page.py` already asserts the strip moves and the bar appears |
| Replay | `tests/test_replay_editorial_routes.py`, `tests/test_matrix_routes.py` | the progress work changed no prompt |
| Parity | extended `tests/test_surface_parity.py` | CLI and UI render the same stage sequence and counts from one run |
| Pipeline | `make test-integration-pipeline` | the CLI surface end to end |
| Docs | `make docs-build` | the pages match the code |

New tests owed:

- An e2e cut over a large fake library asserting the DOM image count stays bounded
  while paging, and that a grid toggle performs no navigation.
- A storyboard test asserting shot order equals capture order and that the timecodes
  sum to the planned duration.
- A progress test asserting every stage a cut emits carries either counts or an
  explicit "no unit", and that no phase name reaches `generate_progress._ranges`
  unmapped.

Manual pass, both audiences: run one memory through the CLI and the same memory
through the UI and diff the stage sequence; then let the scheduler fire and check
that the Runs page shows it.
